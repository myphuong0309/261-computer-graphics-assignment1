# Tutorial 1: Project Overview and the OpenGL State Machine

Welcome to the deep dive into Computer Graphics. To truly understand this project, we must go beyond surface-level analogies and look at the actual architecture of modern graphics programming.

This project uses **C++17** and **OpenGL 3.3 (Core Profile)**. The "Core Profile" is crucial: it means we are using the modern, shader-based programmable pipeline, entirely dropping the outdated "fixed-function" pipeline (like `glBegin()`, `glEnd()`, `glVertex3f()`).

## 1. The Architecture of the Project
Our application is structured using a hybrid Model-View-Controller (MVC) pattern adapted for real-time rendering:

*   **Model (Data & State)**: `AtomData`, `BohrModel`, `MoleculeScene`. These store the absolute truth of our simulation—where atoms are, what color they are, how many electrons they have, and their current animation state.
*   **View (Rendering)**: `Shader`, `Mesh`, and the `phong.vert`/`phong.frag` GLSL scripts. These take the mathematical state and convert it into colored pixels on the screen.
*   **Controller (Logic & Input)**: `main.cpp` and `Camera.cpp`. These handle the window events, capture mouse movements, calculate time deltas (`dt`), and trigger the updates to the Models.
*   **The Glue (Scene Graph)**: `SceneNode.h/cpp`. This bridges the Model and the View by organizing objects hierarchically and calculating their final 3D spatial matrices.

## 2. The OpenGL State Machine
OpenGL is not a standard C++ library with objects and classes. It is a **State Machine** managed by your GPU driver. 
When you call a function like `glBindVertexArray(vao)` or `glUseProgram(shaderID)`, you are flipping a switch on the graphics card. That switch stays flipped until you explicitly flip it back.

Every draw call (e.g., `glDrawElements`) looks at the *current state* of the GPU:
*   "What shader is currently active?"
*   "What geometry buffers are currently bound?"
*   "Is Depth Testing enabled?"

This is why, in `main.cpp` and `SceneNode.cpp`, you will see a pattern of **Bind -> Draw -> Unbind**. We set the state, execute the draw, and clean up the state so we don't accidentally affect the next object we want to draw.

## 3. The Modern Graphics Pipeline (In Depth)
To understand what happens when `mesh->draw()` is called, you need to understand the pipeline:

### Step 1: Vertex Specification (CPU -> GPU)
Before rendering begins, the CPU allocates memory on the GPU (VRAM) and copies arrays of data (Vertices and Indices) into it. This happens once during setup in `Mesh.cpp`.

### Step 2: Vertex Fetch (GPU)
When a draw call is issued, the GPU fetches the vertex data from VRAM based on the configuration defined by the Vertex Array Object (VAO). 

### Step 3: Vertex Shader (Programmable)
For *every single vertex*, the GPU runs our `phong.vert` program. 
The primary job of the Vertex Shader is to apply matrix transformations. It takes the local 3D coordinates of the vertex (e.g., a point on a sphere) and multiplies it by the Model, View, and Projection matrices to figure out exactly where that point lands on your 2D screen (called "Clip Space"). It outputs this to a built-in variable called `gl_Position`.

### Step 4: Primitive Assembly & Clipping (Hardware)
The GPU takes the transformed vertices and connects them into triangles (based on our Indices). If a triangle falls outside the camera's view (outside the screen), the GPU clips it or discards it to save processing power.

### Step 5: Rasterization (Hardware)
The mathematical 3D triangle is converted into 2D "Fragments". A fragment is essentially a potential pixel on your screen. The GPU interpolates data between the vertices. For example, if Vertex A has Normal X, and Vertex B has Normal Y, a fragment exactly in the middle will be given a Normal that is a 50/50 blend of X and Y.

### Step 6: Fragment Shader (Programmable)
For *every single fragment* generated by rasterization, the GPU runs our `phong.frag` program. 
This shader looks at the interpolated Normal, the Light Position, and the Material Colors, and performs complex math (the Phong reflection model) to determine the final `vec4` RGBA color of that specific pixel.

### Step 7: Depth & Stencil Testing (Hardware)
Before writing the color to the screen, the GPU checks the Depth Buffer (Z-Buffer). If another object has already been drawn closer to the camera at this exact pixel, the GPU discards the current fragment. This ensures objects in front correctly block objects behind them.

### Step 8: Framebuffer
The final color is written to the back buffer. In `main.cpp`, `glfwSwapBuffers()` swaps the back buffer with the front buffer, instantly displaying the fully rendered frame to the user.
